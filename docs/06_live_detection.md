# 06 — الكشف الحي: من الحزمة إلى القرار

## 1. التحدّي

النموذج تدرّب على **سجلات اتصالات** جاهزة (41 ميزة). لكن كرت الشبكة يرى **حزماً** (Packets) منفردة. نحتاج "مترجماً" يحوّل الحزم إلى نفس الميزات بالضبط — وإلا سيرى النموذج أرقاماً لا يفهمها.

```
حزم خام ──► PacketInfo ──► Connection ──► صف ميزات ──► HybridIDS ──► تنبيه
(scapy)     (capture.py)   (flow.py)      (flow.py)      (hybrid.py)
```

## 2. الخطوة 1 — تبسيط الحزمة (`capture.py → to_packet_info`)

من كل حزمة نأخذ فقط ما نحتاجه من **الترويسات**:

| الحقل | من أين |
|---|---|
| `timestamp` | وقت التقاط الحزمة |
| `protocol` | tcp / udp / icmp |
| `src_ip`, `dst_ip` | ترويسة IP |
| `src_port`, `dst_port` | ترويسة TCP/UDP (لـ ICMP: نضع **نوع** الرسالة مكان المنفذ) |
| `payload_len` | طول الحمولة (لا نقرأ محتواها) |
| `tcp_flags` | أعلام TCP: S, A, F, R, P, U |

**ملاحظة خصوصية:** لا نقرأ محتوى الحمولة إطلاقاً — فقط طولها. هذا يجعل النظام يعمل حتى مع HTTPS المشفَّر.

## 3. الخطوة 2 — تجميع الحزم إلى اتصالات (`flow.py → assemble_connections`)

**مفتاح الاتصال (5-tuple):** `(بروتوكول، IP مصدر، منفذ مصدر، IP هدف، منفذ هدف)`

- الحزمة A→B والحزمة B→A **نفس الاتصال** (نبحث بالاتجاهين).
- أول من أرسل = **المُبادِر** (originator). بايتاته ← `src_bytes`، وبايتات الطرف الآخر ← `dst_bytes`.
- إذا مرّت 60 ثانية بلا نشاط ← الحزمة التالية تبدأ اتصالاً جديداً.

### تحديد حالة TCP (`flag`) — أهم ميزة سلوكية

نسجّل "أحداث" كل اتصال: هل أرسل المُبادِر SYN؟ هل ردّ المستجيب بـ SYN-ACK؟ من أرسل FIN أو RST؟

```
المصافحة الثلاثية الطبيعية:
   العميل ──SYN──►  الخادم
   العميل ◄─SYN/ACK─ الخادم        ← "established"
   العميل ──ACK──►  الخادم
   ... بيانات ...
   FIN ↔ FIN                      ← SF (مكتمل طبيعي)
```

| الحالة | ما رأيناه | دلالته الأمنية |
|---|---|---|
| **SF** | مصافحة كاملة + إغلاق طبيعي | طبيعي |
| **S0** | SYN فقط، لا رد إطلاقاً | **SYN Flood** أو مسح لأجهزة غير موجودة |
| **REJ** | SYN ← RST | **مسح منافذ** (المنفذ مغلق) |
| **RSTO / RSTR** | أُنشئ ثم قُطع بـ RST | مسح متقدّم أو خلل |
| **SH** | SYN ثم FIN بلا رد | مسح خفي (stealth) |
| **S1** | أُنشئ ولم يُغلق بعد | اتصال جارٍ |
| **OTH** | لم نرَ SYN | بدأ قبل الالتقاط |

## 4. الخطوة 3 — ميزات النوافذ (`connections_to_features`)

لكل اتصال ننظر إلى **الماضي القريب**:

```
الزمن ──────────────────────────────────────────►
  [.... آخر ثانيتين ....] ← الاتصال الحالي
  ← نافذة زمنية: count, serror_rate, same_srv_rate ...

  [c1 c2 c3 ... c254] ← الاتصال الحالي
  ← نافذة الجهاز (آخر 255 اتصالاً): dst_host_count, dst_host_serror_rate ...
```

**مثال SYN Flood:** 3000 حزمة SYN خلال 3 ثوانٍ:
- `count` لآخر اتصال = 511 (الحدّ الأقصى في NSL-KDD — نقصّ القيم لنفس المدى الذي تدرّب عليه النموذج)
- `serror_rate` = 1.0 (كل الاتصالات S0)
- النموذج: "هذا يشبه neptune تماماً" ← **DoS**

**مثال Ping Sweep:** 254 رسالة ICMP Echo لـ 254 جهازاً مختلفاً:
- `service` = `eco_i`، `srv_diff_host_rate` = 1.0 (نفس الخدمة لأجهزة مختلفة)
- ← **Probe** (100% في العرض)

## 5. أنماط التشغيل

> الأسهل: كل هذا متاح من الموقع (`sudo .venv/bin/netsentinel web`). الأوامر أدناه للطرفية فقط.

| الأمر | المصدر | الصلاحيات |
|---|---|---|
| `netsentinel pcap file.pcap` | ملف مسجّل (Wireshark/tcpdump) | لا شيء |
| `sudo netsentinel live --iface en0` | كرت الشبكة مباشرة | root / Npcap |
| `netsentinel baseline normal.pcap` | حركة طبيعية **من شبكتك** | لا شيء |

### كيف يعمل الوضع الحي داخلياً
كل 10 ثوانٍ: نلتقط دفعة ← نضيفها لمخزن آخر 120 ثانية (حتى تبقى النوافذ ممتلئة بالسياق) ← نحسب الميزات ← نُبلّغ **فقط** عن الاتصالات التي بدأت في الدفعة الأخيرة (حتى لا يتكرّر التنبيه).

## 6. لماذا أمر `baseline` مهم جداً؟

NSL-KDD تمثّل شبكة **1998**. شبكة جامعتك اليوم: HTTPS، تحديثات Windows، Teams، YouTube... كاشف الشذوذ سيعتبر الكثير منها "غريباً" ← إنذارات كاذبة.

**الحل:** سجّل ساعة من حركة طبيعية في شبكتك:
```bash
sudo tcpdump -i en0 -w normal_hour.pcap      # اتركه ساعة ثم Ctrl+C
netsentinel baseline normal_hour.pcap
```
يُعاد تدريب كاشف الشذوذ ومعايرة عتبته و"بصمة الطبيعي" على شبكتك أنت، ويُحفظ كنموذج منفصل `hybrid_ids_custom.joblib`. المصنِّف يبقى كما هو (لأنه يحتاج هجمات مُسمّاة).

## 7. العرض الحي في الموقع: "ميدان الهجوم"

في قاعة العرض لا تحدث هجمات حقيقية صدفة، فالمراقبة الحية لن تُظهر شيئاً. لذلك بنينا داخل الموقع **مهاجماً وضحية على نفس اللابتوب**:

| المكوّن | ما هو |
|---|---|
| **الضحية** | خادم ويب صغير على `127.0.0.1:8088` يشغّله NetSentinel نفسه |
| **التصفّح الطبيعي** (مفتاح) | "مستخدم" يطلب صفحة كل 0.3–1.5 ثانية — حتى يظهر الطبيعي على الشريط |
| **المهاجم** (طرفية + أزرار) | `scan` = nmap حقيقي، `service-scan` = nmap -sV، `flood` = 3000 طلب متوازٍ |
| **وضع الهجوم** (مفتاح) | يكرّر الهجمات الثلاث تلقائياً بفواصل 10 ثوانٍ حتى تطفئه |
| **المدافع** | NetSentinel يلتقط على `lo0` (واجهة الجهاز الداخلية) ويحكم كل 3 ثوانٍ |

```
 الطرفية (Attacker):  attacker@range:~$ scan
                      $ nmap -sS -p 1-2000,8088 -T4 -n 127.0.0.1
                      8088/tcp open  radan-http
                      [NetSentinel] ALERT Probe 127.0.0.1 → 127.0.0.1:135   ← بعد ~3 ثوانٍ
```

**لماذا الواجهة `lo0`؟** لأن الهجوم والضحية على نفس الجهاز، فالحزم لا تخرج إلى الـ Wi-Fi بل تمرّ في واجهة داخلية اسمها loopback.

**ملاحظة صادقة:** في هذا الإعداد كل الحركة من `127.0.0.1` إلى `127.0.0.1`، فميزات "آخر الاتصالات لنفس الهدف" تخلط الهجوم بالتصفّح الطبيعي، وقد يُنذَر عن بعض التصفّح الطبيعي **أثناء** الهجوم. على شبكة حقيقية بعناوين مختلفة يقلّ هذا كثيراً.

## 8. ⚠️ الأخلاقيات والقانون

- التقط فقط على شبكة **تملكها** أو لديك **إذن كتابي** بمراقبتها.
- الالتقاط على شبكة الجامعة يحتاج موافقة قسم تقنية المعلومات.
- ملف العرض `demo_attack.pcap` **مصنوع بالكامل** (`tools/make_demo_pcap.py`) ولا يُرسل أي حزمة لأي شبكة — يُكتب في ملف فقط. عنوان "المهاجم" `203.0.113.66` من نطاق مخصّص للتوثيق (RFC 5737) وليس عنواناً حقيقياً.
